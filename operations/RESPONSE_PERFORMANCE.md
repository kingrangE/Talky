# 대화 응답 성능 검증

## 합의한 목표

2026-11-11 사용자와 합의한 기준은 동시 사용자 50명, 첫 텍스트 응답 p95 8초 이내·p99 10초 이내, 오류율 5% 미만이다. 첫 토큰이 아니라 저장된 대화 답변이 관측되는 시간을 측정한다. 영어 표현 교정과 음성은 뒤에 완료될 수 있지만 성공·실패와 전체 완료 시간을 별도로 기록한다.

50명 접속과 50명 동시 전송은 다른 부하 조건이다. 우선 계정 50개가 한 번씩 동시에 전송하는 burst를 사용한다. 지속 사용자 프로필은 응답을 읽는 시간과 다음 발화 간격을 고정한 별도 실험이 필요하다. 최종 p99 판단은 50건의 단일 실행으로 하지 않는다. 최소 1,000건 이상과 반복·독립 구간을 확보한 뒤 꼬리 지연의 변동성을 확인한다. 1,000건 자체가 통계적 보증은 아니다.

## 실행기와 집계 원칙

`operations/load_conversations.py`는 전용 `_test` PostgreSQL의 임의 스키마에 독립 사용자·대화를 구성하고 실제 접수 함수와 감독되는 워커를 실행한다. 종료 시 해당 스키마와 임시 음성만 제거한다. Langfuse 원격 변경과 유료 모델 호출은 하지 않는다. real 모드는 실제 Ollama·교정·Piper를 사용하며 synthetic 모드는 실행기의 회귀 테스트에만 사용한다.

전송 전부터 DB 결과가 보일 때까지 1초 간격으로 관측한다. HTTP·브라우저 렌더링을 포함하지 않은 서버 결과 표시의 대리 지표이므로 이 실행기만으로 실제 서비스 SLO 통과를 선언하지 않는다. 입력 음성의 STT도 이번 텍스트 부하에 포함하지 않는다. 이력이 없는 새 대화 80% 영어·20% 한국어이며 긴 기억 대화를 대표하지 않는다.

p95·p99는 nearest-rank로 계산한다. 접수 실패와 텍스트 미관측 요청을 전체 분모에서 제거하지 않는다. 해당 백분위에 미관측 요청이 걸리면 JSON은 null로 표시하며 지연이 0이라는 뜻이 아니다. 완료 요청에 한정한 전체 완료 p95도 별도 지표임을 명시한다.

접수 실패·작업의 terminal 실패와 실행기의 90초 관측 종료를 구분한다. 관측 종료는 서비스가 영구 실패했다고 판단한 것이 아니다. 단, 90초 동안 답변이 관측되지 않았다면 8초·10초 응답 목표를 충족하지 못한 사실은 확인할 수 있다. 교정 누락과 음성 완료 수 역시 별도로 기록한다. 표본에서 수치가 좋아도 작은 표본·synthetic·브라우저 미포함 조건을 최종 통과로 바꾸지 않는다.

## 최초 기준선

기준 코드는 2681841이며, 최초 실행은 워커 초기화를 포함한다. Apple M2 Pro·메모리 16GiB, 호스트 Ollama ax4-light:latest, Docker Desktop Linux amd64 Python 3.11 음성 런타임에서 실행했다. CPU 음성 성능에는 amd64 실행 환경의 영향이 있으므로 운영 GPU 인스턴스 성능으로 일반화하지 않는다. 추론 슬롯 1, 음성 슬롯 1, 워커 4, 전체 미완료 작업 한도 32, 컨텍스트 16,384, 출력 상한 4,096을 유지했다. 실제 AWS 자원은 사용하지 않았다.

50명 구간에서는 90초 내 텍스트 관측 6건, 10초 이내 관측 0건이다. 접수 실패만으로 오류율 하한은 36%이며 목표 5% 미만을 충족하지 못한다. 28건의 관측 종료 미완료를 더해 서비스의 실제 영구 오류율이 92%라고 주장하지 않는다. 실행기에서 정의한 미완료 포함 비율과 실제 접수 실패 비율을 구분해야 한다.

1명 구간은 기억 회상 11.529초, 답변 생성 5.058초, 교정 3.566초 후 텍스트가 저장됐다. 음성은 추가 9.388초였다. 추론 대기 p95는 약 0.013초로 이 요청의 지연은 슬롯 대기만으로 설명되지 않는다. 50명 구간에서는 추론 대기 p95 14.097초도 발생했다. 작업 전체를 슬롯 밖으로 옮긴 것만으로 충분한 처리 용량을 확보한 것은 아니다.

원시 결과·단계 로그는 `experiments/conversation-load-baseline-20261111-v2/`에 있다. `operations/analyze_conversation_load.py`로 저장된 로그를 다시 집계할 수 있다. 최초 운영 이미지 실행은 Git 실행 파일이 없어 시작 전 실패했고 사용자 요청은 전송하지 않았다. 실행기는 이후 Git이 없는 이미지에서도 revision 환경값과 실행기 해시를 기록하도록 보완했다.

## 다음 비교 조건

워커 초기화와 모델 준비 비용을 구분하기 위해 같은 실행기에 `--warm-workers` 모드를 추가했다. 준비 모드는 그래프·모델 객체와 Piper를 로드한 뒤 요청을 전송한다. 모델 서버 자체는 공유되므로 최초 로드와 외부 요청 간섭을 완전히 통제한 전용 추론 서버 실험은 아니다. 실제 모델의 토큰 처리량과 GPU 이용률 측정도 추가로 필요하다.

답변 생성 후 교정을 기다리던 경로를 바꿔, 핵심 답변을 먼저 원자적으로 저장하고 교정 결과만 나중에 보완한다. 메시지는 추가 생성하지 않으며 요청 시도와 소유권을 검사한다. 그래프 동기화에서는 교정 보완이 토픽 가중치를 다시 올리지 않도록 한다. 변경 전 사본과 변경 후 코드에 같은 부하 실행기를 적용한다. 샘플에서 개선되더라도 50명 목표 충족 여부와 분리해 판단한다.

현재 우선순위는 (1) 교정을 첫 텍스트 경로에서 분리, (2) 기억 검색·토픽 추출 비용과 추론 슬롯 대기 분석, (3) 음성 작업이 요청 워커를 오래 점유하는 현상 검토, (4) 실제 추론 서버의 처리량에 맞춘 용량 결정이다. 전체 큐를 32에서 50 이상으로 늘리기만 하면 접수 실패 대신 긴 대기가 늘 수 있으므로 이것만으로 해결됐다고 판단하지 않는다.

## 교정 분리 후 순차 비교

전체 회귀 테스트를 마친 뒤 다른 회귀 작업을 함께 실행하지 않고 수정 전 2681841과 수정 후 5f6d679를 순차 비교했다. 두 실행은 같은 실행기 SHA256 `2b0ed437e76b1726280dcb36ba295fdcd737e88d4c2629a8b187f86b79e0174c`, 모델·컨텍스트·워커 4개·슬롯 1개와 `--warm-workers` 조건을 사용했다. 50명 구간 전에 각각 1명 구간을 수행했다. 실제 모델 서버가 전용으로 격리된 것은 아니므로 공유 서버 상태와 캐시·온도·실행 순서의 영향을 완전히 통제했다고 주장하지 않는다.

단일 요청에서 보이는 21.362초→11.439초 차이를 통계적으로 입증된 개선율로 해석하지 않는다. 수정 전 기억 회상은 11.481초였고 수정 후에는 6.667초여서 교정 분리 외의 실행 변동도 포함된다. 변경으로 보장하는 것은 교정이 끝나기 전에 본문이 저장되어 읽힌다는 동작이며, 멈춘 교정을 주입한 통합 테스트로 검증했다. 부가 결과는 같은 메시지에 반영하고 이전 시도·다른 사용자 수정은 차단한다.

50명에서는 완료 수가 늘지 않았고 오히려 해당 표본에서 감소했다. 처리량 개선이 입증됐다고 볼 수 없다. 수정 후 1명도 10초를 넘었고 50명 목표는 미달이다. 모델 슬롯 대기와 기억 회상·생성 호출, 음성을 처리하는 동안 워커가 다음 작업을 가져오지 못하는 구간을 추가로 해결해야 한다. CPU 음성과 모델 자원 슬롯을 나눴어도 워커 전체 작업 생명주기가 자동으로 분리되는 것은 아니다.

50명 구간의 네 워커 합계 최대 관측 RSS는 수정 전 약 2.24GiB, 수정 후 약 2.34GiB였다. 이는 호스트 모델과 Docker VM·부하 조정 프로세스·다른 앱 메모리를 제외하며 GPU 이용률을 측정한 값도 아니다. 원본은 각 result.json의 resource_samples에 있다.

원시 결과는 `experiments/conversation-load-warm-before-final-20261111/`, `experiments/conversation-load-warm-after-final-20261111/`에 있다. 이전 `conversation-load-warm-before-20261111/`는 일부 구간에서 회귀 테스트의 DB 경합이 섞여 메타데이터에 그 사실을 표시했으며 위 비교 근거에서 제외했다. 관련 코드 전체 회귀 테스트 169개가 통과했다.

## 접수 한도만 64개로 바꾼 대조 실험

수정 후 코드의 운영 기본값은 그대로 두고, 테스트 컨테이너 환경에서만 CONVERSATION_QUEUE_LIMIT=64를 적용했다. 같은 모델·슬롯·워커·90초 관측 조건에서 50건 모두 접수됐고 접수 실패는 0건이었다. 90초 안 텍스트 관측은 13건, 전체 완료는 11건, 관측 종료 시 미완료는 39건이었다. 가장 빠른 텍스트 관측도 14.366초였고 10초 이내 관측은 0건이었다. 따라서 접수 제한을 완화하는 것만으로 응답 목표가 해결되지 않음을 확인했다.

이 실험에서 39건은 실행기 관측 종료이며 영구 서버 오류로 분류하지 않는다. 반대로 접수 실패 0건만 보고 오류율과 전체 SLO를 통과했다고 주장하지 않는다. 미관측 요청을 포함하면 첫 텍스트 p95·p99는 비유한 상태이며 지연 목표가 명확히 미달이다. 단일 실행의 처리 완료 수 증가 역시 캐시·서버 상태·출력 길이 변동이 있어 한도 변경의 처리량 개선 효과로 단정하지 않는다. 원시 결과는 `experiments/conversation-load-queue64-20261111/`에 보존했다.

## 후속 작업의 순서와 종료 기준

1. 대화 핵심 작업과 교정·음성 후처리를 영속 작업 단위로 나누고, 후처리 대기가 모든 대화 워커를 점유하지 않게 한다. 단순 백그라운드 스레드로 옮겨 재시작 시 결과를 잃는 방식은 피한다. 기존 요청 ID, 시도 fencing, 부분 결과 표시와 삭제 보장을 유지하며 장애 주입으로 검증한다.
2. 첫 답변 전 기억 질의용 모델 호출의 필요성과 비용을 분리한다. 검색을 생략해 수치만 줄이지 않고 동일 기억 평가셋에서 근거 회수·날조·답변 품질을 비교해 대안을 선택한다. 현재 수정 후 단일 요청의 기억 회상 6.667초와 답변 생성 3.734초만으로도 p95 8초 목표를 넘는다는 점을 우선 다룬다.
3. 전용 추론 서버에서 동시 처리·배치·출력 길이별 실제 용량을 측정한 뒤 모델 슬롯과 접수 한도를 맞춘다. 슬롯 수나 큐를 늘리는 것만으로 GPU 처리량이 늘어난다고 가정하지 않는다. 현 로컬 장비의 결과를 AWS GPU 서버 성능으로 외삽하지 않는다.
4. 대표 이력 길이, 한국어·영어·음성 입력, 사용자의 다음 발화 간격을 고정한 지속 50명 프로필을 실행한다. 실제 HTTP·Streamlit 화면에서 첫 유용한 텍스트가 표시되는 시각을 측정하고 p95 8초·p99 10초, 오류율 5% 미만을 반복 확인한다. 오류율은 전체 시도를 분모로 기록하고, 접수된 요청의 실패·시간 초과를 지연 표본에서 조용히 제거하지 않는다. 정상 응답에 한정한 백분위도 함께 제시해 지연과 가용성의 해석을 분리한다.

현재 결과는 목표 미달이며 #6·#7의 운영 성능 검증을 완료 처리하지 않는다. 기존 기능 테스트 통과와 응답의 조기 저장은 확인됐지만 목표 동시 사용자 처리 용량 확보는 별도 과제로 남아 있다.

## 실행 예

Piper가 준비된 Linux 환경과 전용 PostgreSQL·Neo4j, 명시한 로컬 Ollama 모델이 필요하다. 호스트 Python에서 Piper를 사용할 수 없으면 기존 운영 이미지의 /opt/talky/audio 캐시를 사용한다. Docker용 DSN·모델·Neo4j 주소에는 컨테이너에서 접근 가능한 호스트 이름을 지정한다.

```bash
# TALKY_TEST_POSTGRES_DSN은 컨테이너에서 접근 가능한 전용 *_test DB로 설정한다.
docker run --rm --platform linux/amd64 \
  -v "$PWD:/app:ro" -v "$PWD/operations/experiments:/reports" \
  -e TALKY_TEST_POSTGRES_DSN \
  -e MODEL_NAME=ax4-light:latest \
  -e OLLAMA_BASE_URL=http://host.docker.internal:11434 \
```

교정 조기 저장, 소유권·이전 시도 차단, 그래프 토픽 중복 방지, 부하 실행기와 집계를 포함해 전체 테스트 170개가 통과했다. 완료 지연은 정상 완료된 요청만으로 집계하고 실패 종료 시간으로 수치를 낮추지 않으며, 실패는 전체 시도 오류 집계에 남기는 회귀 테스트도 포함한다. PostgreSQL·Neo4j와 실제 백업·복구를 사용했다. LangChain의 향후 기본값 변경 경고 1개가 남아 있다. 기능 회귀 통과와 50명 응답 SLO 통과는 별개의 결과이며 후자는 미달이다.

## 가벼운 기억 검색 사전 판정

별도 LLM·DB 호출 없이 현재 발화 전체를 정규화해 명확한 인사·감사·작별 표현 집합과 비교한다. 인사 뒤에 개인 질문이 붙은 문장은 전체 일치가 아니므로 검색을 유지한다. 최근 두 메시지에 과거 기억을 가리키는 단서가 있으면 짧은 인사라도 검색으로 되돌린다. 'Yes', 'Okay', 모호한 지칭, 개인 사실이나 일반 업무 발화는 확실한 생략 대상으로 간주하지 않는다. 분류 이유만 memory_gate 이벤트에 기록하며 사용자 발화 원문은 로그에 넣지 않는다.

이 판정은 기존 기억 회상 노드의 토픽 추출 이전에 실행한다. 생략 시 토픽 추출 모델·Neo4j·검색 결과 소유권 필터 DB 조회를 호출하지 않지만, 이후 답변 생성·대화 저장·Outbox 원문 투영은 그대로 진행한다. 의미 있는 개인 사실을 담은 발화는 기존 토픽 생성 경로를 유지하므로 이번 변경을 위해 색인용 모델 호출을 새로 추가하지 않는다. 모델 시간 예산 예약도 실제 검색 경로에서만 적용해 가벼운 분기가 60초 호출 예산을 요구하지 않게 했다.

규칙 판정 CPU 진단은 `python -m operations.check_memory_gate`로 다시 실행할 수 있다. 원시 수치는 experiments/memory-gate-cpu.json에 보존한다. 현재 측정에서 판정 자체는 p95 약 1마이크로초 수준이었지만 모듈 초기화·로그·네트워크·답변 생성 시간은 포함하지 않는다. 기존 기억 90문항은 모두 검색 경로를 유지했고, 검색 생략 시 모델·DB 호출이 없으며 원문이 저장·투영되는 통합 검증을 포함해 전체 테스트 188개가 통과했다. 이는 기존 문항의 라우팅 검증이며 전체 답변·judge 평가 재실행이나 실제 사용자 전반의 판정 정확도를 입증한 결과는 아니다.

보수적인 초기 버전이므로 기존 50명 부하의 업무 발화 5종은 모두 검색을 유지한다. 따라서 이 판정만으로 기존 부하의 p95·p99가 개선됐다고 주장하지 않는다. 생략 범위를 확장하려면 최근 대화까지 포함한 검색 필요·불필요 라벨을 만들고, 필요한 검색을 잘못 생략하는 비율과 실제 혼합 부하 지연을 함께 확인해야 한다.
